# [2026-05-29] Stage3 浮点精度泄露修复

## 背景

山寨币阶段三脚本 `stage3-executor.js` 在拆分 OCO 两档止盈止损仓位时，传 `--sz` 参数给 OKX 被拒绝。用户手动补单时发现：OKX 日志中的 `--sz` 值带有 IEEE 754 浮点精度尾巴 `2.3000000000000003`，而非干净的 `2.3`。

此次修复由用户现场发现并指明根因后执行。

## 症状

OCO 下单三次重试全部失败，日志显示：

```
--sz 2.3000000000000003
```

OKX 合约 `lotSz=0.1`，不接受 `2.3000000000000003` 这种浮点尾巴值。

## 根因分析

`alignToLot` 函数中 `Math.floor(v / lotSz) * lotSz` 产生不可见的浮点精度泄露：

| 表达式 | JS 实际值 | 预期值 |
|--------|----------|--------|
| `23 * 0.1` | `2.3000000000000003` | `2.3` |
| `24 * 0.1` | `2.4000000000000004` | `2.4` |

原因：`0.1` 在 IEEE 754 双精度浮点中无法精确表示（≈ `0.1000000000000000056`），乘以整数后累加误差。这个尾巴对 JS 来说是透明的（因为 `2.3000000000000003.toFixed(2) === "2.30"`），但 OKX 后端严格解析 `--sz` 字符串，直接拒绝非标准精度值。

影响范围：`stage3-executor.js` 中 `executeOpen`、`executeAdd`、`executeReduce`、`executeAdjust` 四个操作函数的仓位拆分逻辑。

## 修复内容

### Bug 修复

| 位置 | 原代码 | 修复后 |
|------|--------|--------|
| `alignToLot`（×4 处定义） | `Math.floor(v / lotSz) * lotSz` | `round(Math.floor(v / lotSz) * lotSz, 8)` |
| `rawSzTp1` 计算（open/add） | `sz * ratio1` / `totalSz * ratio` | `round(sz * ratio1, 8)` |
| `remaining` 计算（open/add） | `sz - szTp1` | `round(sz - szTp1, 8)` |
| `remaining` 计算（reduce） | `remainingSz - szTp1` | `round(remainingSz - szTp1, 8)` |
| `executeOpen` sz 初始取整 | `Math.round(rawSz / lotSz) * lotSz` | `round(Math.round(rawSz / lotSz) * lotSz, 8)` |
| `executeAdjust` | 用魔数 `Math.round(v * 10000) / 10000` 硬除 | 提取 lotSz + 统一用 `alignToLot` |

### 原则确立

**所有传给 OKX `--sz` 参数的值，在最后一步必须经过 `round()` 消除浮点尾巴。** 此条已写入 `TOOLS.md` 陷阱区。

## 涉及文件

| 文件 | 改动 |
|------|------|
| `scripts/stage3-executor.js` | 7 处修改，覆盖 open/add/reduce/adjust 四个操作函数 |
| `TOOLS.md` | 陷阱区"OCO 拆分张数必须对齐 lotSz"条目更新，新增浮点精度泄露子条目 |

## 已知遗留

无。

## 后续建议

- `calc-position.js` 等其他涉及 sz 计算的脚本应做同样的浮点安全检查。
- 考虑写一个 `sanitizeSz(v, lotSz)` 共享工具函数，不再在每个函数内重复定义 `alignToLot`。
