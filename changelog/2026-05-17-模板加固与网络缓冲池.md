# [2026-05-17] 模板加固 + 网络事件缓冲池 + 静默错误分析

## 背景

凌晨巡检发现 `ACT-taker-anomaly.js` 持续报 `Parameter period error`（每 5 分钟一次），但自愈系统从未察觉。同时 `JTO-taker-ratio.js` 因属性名错误静默不工作，两条规则持续浪费 API 请求。

此前 5 月 16 日的修复主要针对死亡循环和触发即归档问题，未从根因上处理「异常被吞掉」的模式。本次是一次系统性审查：隐藏错误如何在模板→API→引擎三层之间形成沉默链条，并加固薄弱环节。

## 症状

| 现象 | 数据 |
|------|------|
| `Parameter period error` 重复出现 | 00:01 → 00:05 → 00:10 → 00:15 每 5 分钟一次 |
| `instType无法识别` 警告 | `http://127.0.0.1:7890` 被当 instType 传入 |
| JTO taker 规则静默不工作 | `takerData.ratios` → `undefined` → 进入「无数据，跳过」分支，不抛错 |
| 网络异常通知过于频繁 | 每次网络波动即时通知，无汇总 |
| 通知内容过于简略 | 只写「X条规则受影响」，不列具体规则名和恢复状态 |

## 根因分析

### 根因 1：check() catch 块写 `return false` 替代 `throw error`——唯一最危险的位置

模板 `set-alert.md` 明确写 `throw error; // 必须抛出，让引擎监控到错误`，但模型在生成 `ACT-taker-anomaly.js` 和 `ORDI-taker-sustained.js` 时写成了 `return false`。

`return false` 的破坏机制：
```
API 报错 → check() catch 捕获 → return false → 引擎看到「检查正常，未触发」
                                                              ↓
                                                      自愈系统：consecutiveErrors 永远为 0
```

引擎判断规则健康的唯一信源是 `check()` 是否抛异常。`return false` 让引擎收到一个完美的 false——自愈系统不可能知道有问题。这不是模板的错，是模型偏离模板。但模型写新规则时会反复出现，无法靠人工审查每一条。

### 根因 2：sanitizePeriod / sanitizeInstType 静默接受非法参数类型

`sanitizePeriod({ proxy: '...' })` 收到对象时不报错，返回对象本身。URL 拼接时 JS 隐式 toString → `period=[object Object]` → OKX 返回 `Parameter period error`。

```javascript
function sanitizePeriod(period) {
  if (!period) return '1D';
  return PERIOD_NORMALIZE_MAP[period] || period;  // ← 对象原样返回，不 throw
}
```

类似地，`sanitizeInstType({ proxy: '...' })` 静默返回 `'SWAP'` 并打一个 `console.warn`——不报错，上了日志也可能被忽略。

### 根因 3：JS 动态类型不校验返回值属性名

`takerData.ratios` 写成 `takerData.history` 不会报错——访问不存在的属性返回 `undefined`，`!undefined === true`，进入「无数据，跳过检查」分支，静默退出。

API 返回结构没有 Schema 合约，模型凭记忆写属性名，写错不报错。这是 JavaScript 动态类型的先天脆弱点，不是具体某行代码的问题。

### 根因 4：网络事件通知设计为「每次异常即时触发」

`adjustIntervalForNetworkError()` 末尾直接调用 `notifyShisiyue()`，仅有 5 分钟简单去重。网络波动集中爆发时仍然骚扰频繁，且通知内容不含具体规则名和恢复状态。

## 修复内容

### 模板加固

| 文件 | 改动 | 原因 |
|------|------|------|
| `tasks/set-alert.md` §2 | 新增「防御性检查清单」表格（5 条静默错误模式 + 正确/错误示例） | 模型在写规则前必须阅读完整的静默错误图谱 |
| `tasks/set-alert.md` §3.0 新增 | 独立章节「check() 的 catch 块绝对禁止 return false」，含引擎失效链路解释 + 唯一正确形式 | 让模型理解为什么 `return false` 比写错逻辑更致命 |
| `tasks/set-alert.md` §3.1 之前 | 所有 catch 示例后的注释从 `// 必须抛出` 升级为醒目标注 `// ← 必须 throw，不能 return false` | 写代码时的拉回触发点 |
| `tasks/set-alert.md` 完整示例 | catch 块注释升级 + 新增数据非空检查示例（`if (!ticker || typeof ticker.price !== 'number')`） | 示范防御性编程 |

### 网络事件缓冲池

| 文件 | 改动 | 原因 |
|------|------|------|
| `engine.js` | 新增 `networkEventBuffer[]` + `recordNetworkEvent()` + `flushNetworkSummary()` + `scheduleNetworkSummary()` 四个函数 | 替代原有即时通知机制，改用 4 小时窗口汇总 |
| `engine.js` `adjustIntervalForNetworkError()` | 删除 `notifyShisiyue()` 调用，替换为 `recordNetworkEvent('adjusted', ...)` | 网络调整不再即时通知 |
| `engine.js` `runRule()` NETWORK_RESTORED 处 | 新增 `recordNetworkEvent('restored', ...)` | 恢复事件也记入缓冲池 |
| `engine.js` main() | 新增 `scheduleNetworkSummary()` 启动调用 | 启动时安排 4 小时汇总定时器 |
| `engine.js` SIGINT/SIGTERM | 新增 `flushNetworkSummary()` | 关闭前刷新缓冲数据不丢失 |

## 设计边界（不修复）

| 项目 | 原因 |
|------|------|
| API 层 type guard（sanitizePeriod 等） | 用户要求仅改模板。当前依赖模板指引模型不要传错参数类型 |
| 引擎层静默错误检测 | 在 check() 返回 false 时统计「连续 N 次 false + 从未触发」可标记无效规则，但本次未涉及 |

## 后续建议

1. 例行巡检之前修复的 5 条规则和 `ORDI-taker-sustained.js`，确认 catch 块全部使用 `throw error`
2. 考虑在 API 层的 sanitize 函数中加入类型守卫——这是防止参数错位导致静默错误的最后防线，而且成本极低（每个 sanitize 函数加 3 行 if）
3. 引擎可考虑对「连续 N 次 check() 返回 false 且从未触发」的规则输出一条 WARN 日志——逻辑规则正常，但 OI/taker 类规则不正常。当前引擎对此完全没有感知
