# [2026-05-16] 警报器引擎网络错误雪崩防护（方案四）

## 背景

5 月 16 日 13:42 CST，物理网络中断导致所有规则无法访问 OKX API。59 条活跃规则在 2 小时内产生 ~1,800 次 TLS/ECONNRESET 错误，每条约 15 分钟到达 `consecutiveErrors == 5` 阈值 → 67 条规则几乎同时触发自愈 → 135 个 AI 诊断任务瞬间 spawn → 模型费用飙升 + 通知轰炸十四月。

## 症状

| 现象 | 数据 |
|------|------|
| 网络错误总数（13:00-15:00） | **~1,800 次** TLS/ECONNRESET |
| 触发自愈的规则数 | **67 条**（去重） |
| 自愈任务 spawn 总数 | **135 次**（部分规则 13:xx + 14:xx 两波） |
| 峰值密度 | **37 个 spawn / 分钟**（14:31 CST） |
| 十四月通知 | **67 条逐规则通知**（未去重） |
| 被误归档的规则 | 数十条（自愈失败 → 第二次阈值 → `archiveRule`） |
| 网络恢复后残留错误 | 21:45 仍有规则报 TLS 错误 |

## 根因分析

### 根因：所有规则共享同一网络中断根因，但引擎逐规则独立判断

`handleRuleError()` 对每次失败无差别递增 `consecutiveErrors`，不区分错误类型。网络中断时：

```
T+0min:  59 规则全部失败 → consecutiveErrors = 1
T+3min:  全部失败 → = 2
T+6min:  全部失败 → = 3
T+12min: 全部失败 → = 4
T+15min: 全部失败 → = 5 → 67 条同时 spawnSelfHeal()
```

每个自愈 spawn 启动一个隔离的 AI 会话 → 调用 `deepseek-v4-pro` 诊断 → 诊断到 C 类（网络问题）→ 仅做 interval 翻倍 → 但翻倍时网络已恢复 → 部分规则已因二次阈值被归档。

核心矛盾：网络问题不需要 AI 诊断，不应该消耗模型资源。

## 修复内容

### 架构改动

| 文件 | 改动 | 原因 |
|------|------|------|
| `engine.js` | 新增 `isNetworkError()` — 7 个正则匹配 TLS/ECONNRESET/ETIMEDOUT 等网络层错误 | 错误分类前置，不依赖 AI |
| `engine.js` | 新增 `adjustIntervalForNetworkError()` — 引擎内置间隔翻倍（上限 15min）+ 全局通知去重（5min） | 替代 AI 自愈任务的翻倍逻辑 |
| `engine.js` | 新增 `restartRuleTimer()` — 公共定时器重启 | 间隔调整时复用 |
| `engine.js` `handleRuleError()` 顶部 | 网络错误拦截：`isNetworkError → adjustInterval → return false` | 网络错误不进入自愈管道 |
| `engine.js` `runRule()` 正常返回前 | 网络恢复检测：`originalInterval != null → 恢复原始间隔` | 网络恢复后自动回退 |
| `engine.js` `getErrorStats` / `resetErrorStats` | 新增 `originalInterval` 字段 | 存储网络调整前的原始间隔 |
| `engine.js` `startRuleTimer` / `reloadRule` | `activeRules` 新增 `module` 引用 | 供网络恢复时调整间隔使用 |

### 核心逻辑

```
catch 到错误
  ├─ isNetworkError? NO → 现有流程（累计 consecutiveErrors → 自愈）
  └─ isNetworkError? YES →
      ├─ consecutiveErrors 不递增（永不触发自愈）
      ├─ 首次网络错误 → 间隔翻倍（3→6→12→15min 上限），日志 NETWORK_ADJUSTED
      ├─ 已调整过 → 跳过
      └─ return false（不暂停规则）

规则正常执行成功
  └─ originalInterval != null → 恢复原始间隔，日志 NETWORK_RESTORED
```

### 网络错误匹配模式

```javascript
/TLS socket disconnected/i
/Client network socket disconnected/i
/read ECONNRESET/i
/ETIMEDOUT/i
/ECONNREFUSED/i
/socket hang up/i
/请求超时/
```

历史自愈数据中覆盖率 100%（本次事故 134 条网络自愈全部匹配），且与代码类错误（`SyntaxError` / `ReferenceError` / `TypeError`）无重叠。

## 设计边界（不修复）

| 项目 | 原因 |
|------|------|
| DNS 错误（`ENOTFOUND` / `EAI_AGAIN`） | 历史零出现。若代码构造错误 URL 导致 DNS 失败，会被误判为网络错误。后果轻微（翻倍间隔 + 不触发 AI 诊断），正常检查时其他异常仍会暴露 |
| 网络错误和代码错误交替 | 概率极低，网络错误通常是全有或全无，不会和代码错误交替出现 |
| 全局网络中断检测 | 未实现。当前方案依赖逐规则的 `isNetworkError` 前置拦截，全局检测作为下一层保护待后续追加（方案一） |
| 规则加载阶段的网络错误 | `loadSingleRule()` 中的 `handleRuleError` 也走同一管道，加载阶段网络错误同样被拦截 |

## 后续建议

1. 追加方案一（全局网络中断检测）：当 N 分钟内 >X 条不同规则报同类网络错误时，冻结全局错误累加，单条通知
2. 追加方案三（自愈任务去重）：同 `rootCause` 的自愈任务已存在时，跳过 spawn 复用已有
3. 监控 `NETWORK_ADJUSTED` 和 `NETWORK_RESTORED` 日志频率，评估网络稳定性
