# [2026-06-15] 数据层独立与仓位变动监控替代止盈止损警报

## 背景

系统存在多个组件独立调用 OKX API 获取实盘仓位数据，形成冗余调用。同时阶段四强制模型在 TP/SL 价位设立警报规则，这层监控完全可以通过实盘仓位变化来实现，无需额外警报。

## 症状

- Dashboard 和 mirror-bot 各自调用 `okx account positions`，同一份数据拉两次
- mirror-bot 职责混杂：既做数据轮询写缓存，又做镜像交易
- 阶段四要求模型为每个开仓周期设立 SL/TP 价位警报，增加模型负担
- mirror-bot 日志中频繁出现 `sCode 51169`（目标仓位已不存在仍尝试操作）

## 根因分析

1. **数据源冗余**：Dashboard (30s) 和 mirror-bot (5s) 都调 `okx account positions --profile live`，拿同一份仓位数据
2. **进程职责混杂**：mirror-bot 同时承担数据采集（写共享缓存）和交易执行（镜像跟单），两者生命周期和关注点不同
3. **警报冗余**：OCO 止盈止损触发 → 仓位归零，这个过程完全可以通过仓位快照比对检测，无需额外价格警报
4. **缺少操作前置检查**：mirror-bot 在减仓/平仓前未验证目标账户是否仍有该仓位，导致对已平仓的位置重复操作

### 仓位变化判别逻辑

通过 OKX fills 记录的 `tag` 和 `clOrdId` 字段区分操作来源：

| fill 标记 | 来源 | 监控动作 |
|-----------|------|---------|
| `tag="CLI"` | stage3 `swap close`（模型手动操作） | **跳过** |
| `clOrdId=O...` | algo 触发（OCO/trail stop 自动平仓） | **触发** |
| 两者都无 | Web/App 外部操作 | **触发** |

触发动作：
- 仓位部分减少 → 派发 `stage1-instant` 即时分析
- 仓位完全归零 → 自动归档周期 + 规则清零 + 复盘 cron

### 进程架构（重构后）

```
data-monitor (5s)          ← 唯一 OKX live 数据源
  ├→ okx-positions-cache.json
  │    ├→ Dashboard (前端显示)
  │    ├→ mirror-bot (镜像交易数据源)
  │    └→ data-monitor 自身 (仓位变动检测)
  │
  └→ 仓位变化检测
       ├→ fills 判别来源 → 外部事件 → dispatch 即时分析
       └→ fills 判别来源 → 仓位归零 → archive-cycle
```
