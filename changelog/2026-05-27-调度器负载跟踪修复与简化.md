# 调度器负载跟踪修复与简化

**日期**: 2026-05-27 11:38
**严重度**: 中 — 影响仪表盘显示和负载计算准确性，未造成任务调度故障
**影响范围**: cron-dispatcher 的 activeJobs 窗口跟踪、dashboard 即时负载显示

---

## 问题一：仪表盘即时负载显示翻倍

### 现象
dashboard 即时负载显示 6 个活跃任务，实际 cron list 中只有 3 个。每个任务出现两次：`source: internal` 和 `source: cron`。

### 根因
`importCronJobs()` 每 5 秒从缓存读取 gateway cron list 并创建 `cron` 条目。调度器 `executeCronAdd` 成功后会写 `internal` 条目。两者按同任务名共存于 `activeJobs`，`/details` 和 `/status` 端点无去重逻辑。

### 修复
第一版：`importCronJobs` 跳过同名 internal 已存在的 cron 条目。后在新设计中改为 cron 替换 internal（见问题三）。

---

## 问题二：已完成任务显示 0m/0m + 负载为零

### 现象
任务 NEIRO 刚刚派发并运行中，但 dashboard 显示 `0m/0m`，`/status` 报负载为 0。

### 根因
两个因素叠加：
1. cron list 缓存每 30s 刷新一次，`importCronJobs` 每 5s 读取。刚派发的任务在缓存中还没出现。
2. 孤儿清理逻辑使用函数顶部捕获的陈旧 `now` 变量，`Math.min(windowEnd, now + 60s)` 把几秒前才创建的 internal 条目窗口缩到只有 ~5 秒。

### 修复
第一版：增加 60s 年龄检测 + 2min 最小窗口。后随新设计整体移除（见问题三）。

---

## 问题三（根本性修复）：internal 条目设计简化

### 原设计的问题

```
旧设计:
  internal 条目 (10min 窗口) → cron 出现 → 两者共存 → computeLoad 去重
                               ↓ cron 消失 → 孤儿清理 → 缩窗 → 各种边界 bug
```

核心谬误：认为 `internal` 条目需要在任务跑完后仍持久占用模型槽位，因为「LLM 会话可能还在跑」。实际上 `delete-after-run` 意味着 cron 被删除时任务已经完成，不需要继续占槽位。

### 新设计

```
新设计:
  internal 条目 (2min 窗口) → cron 出现在列表 → internal 删除，cron 接替
       ↓                              ↓
  填补 ~30s 缓存间隙             gateway 权威窗口数据
                                       ↓
                               cron 消失（任务完成）→ 下轮自然清除
```

`internal` 条目的唯一作用：填补「派发完成 → cron 缓存刷新可见」的 ~30 秒间隙。2 分钟窗口足够覆盖。

### 具体改动

| 改动 | 说明 |
|------|------|
| 新增 `INTERNAL_WINDOW_MS = 2min` | internal/pending 专用窗口，DEFAULT_DURATION_MS(10min) 留给长任务 cron |
| cron 出现时**替换** internal | 不再共存去重，直接 `activeJobs.delete(internal)` 然后设 `cron` |
| **删除孤儿清理逻辑** | 整个 ~30 行缩窗/年龄检测/最小窗口代码移除 |
| `pending` 条目同步改 2min | 仅用于同 tick 防重派发，spawn 回调中即删 |

### 修改文件
`scripts/cron-dispatcher.js` — 约 -40 行 / +15 行，净减 25 行
