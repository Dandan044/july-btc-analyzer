# [2026-05-23] 警报器 429 误判修复与并发控制

## 背景
警报引擎运行时大量规则同时触发 OKX API 限流（HTTP 429），导致：429 错误未被引擎识别为网络错误，走自愈 spawn 流程而非自动翻倍间隔；79 条活跃规则无并发上限，同周期集中发送请求加剧限流。

## 症状
1. 引擎日志频繁出现 `[❌警报检查错误] Too Many Requests`
2. 每条 429 规则积满 5 次错误后 spawn LLM 会话执行 `alert-self-heal.md`，而不直接在引擎层翻倍间隔
3. 多规则同时向 OKX 发送请求，缺乏背压控制

## 根因分析

### Bug：`isNetworkError()` 缺失 429 模式
| 文件 | 根因 |
|------|------|
| `skills/btc-alert/engine.js` `isNetworkError()` | `NETWORK_PATTERNS` 包含 `ECONNRESET`、`ETIMEDOUT` 等网络层错误，但不包含 HTTP 429 `Too Many Requests` |

此缺失导致 429 错误未被引擎的前置网络拦截捕获，而是走常规错误路径 → 5 次后 spawn 自愈 LLM 会话 → LLM 再翻倍间隔。设计流程本应是引擎直接识别并翻倍，无需 LLM 参与。

### 缺陷：无并发上限
| 文件 | 根因 |
|------|------|
| `skills/btc-alert/engine.js` | `runRule()` 中各规则 `check()` 调用无全局并发控制 |

79 条规则虽有 500ms 启动错位，但各自 `setInterval` 独立运行，无跨规则背压机制。当多条规则间隔对齐在同一秒窗口时，瞬时并发可超 OKX 安全速率（5 req/s）。

## 修复内容

### Bug 修复
| 文件 | 问题 | 修复 |
|------|------|------|
| `skills/btc-alert/engine.js` L274 | `NETWORK_PATTERNS` 缺少 429 识别 | 新增 `/Too Many Requests/i` |

### 架构改动
| 文件 | 改动 | 原因 |
|------|------|------|
| `skills/btc-alert/engine.js` L54-72 | 新增并发门控模块：`MAX_CONCURRENT_CHECKS=3`、`acquireSlot()`、`releaseSlot()` | 限制同时执行 API 调用的规则数 |
| `skills/btc-alert/engine.js` `runRule()` | `check()`/`collect()`/`trigger()` 包裹在 `acquireSlot()`...`releaseSlot()` 中 | 最多 3 条规则并发，超出的排队等待 |

## 运维操作
| 操作 | 执行内容 |
|------|---------|
| `pm2 restart btc-alert && pm2 save` | 重启警报引擎使修改生效 |

## 设计边界（不修复）
| 项目 | 原因 |
|------|------|
| Token Bucket 精确速率控制 | 当前并发限制方案（max 3）配合 500ms 启动错位已足够，无需引入更复杂的速率计数器 |

## 后续建议
- 监控重启后 429 错误频率，若仍频繁出现可考虑将 `MAX_CONCURRENT_CHECKS` 降至 2
- 429 自动翻倍后的网络恢复检测（`NetworkRecovery`）已有机制，无需额外改动
