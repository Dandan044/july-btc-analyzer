
## 警报器时间单位大小写问题分析（23:25）

Dandan 要求分析警报器自愈系统检测到的小概率时间单位大小写错误问题。

### 四次自愈记录

| # | 时间 | 规则 | 错误 | 根因 |
|---|------|------|------|------|
| 1 | 05-08 ~14:00 | RLS多价位延迟确认监控 | API错误 | `getOKXKlines` 默认 `instType='SPOT'`，RLS 无现货 |
| 2 | 05-08 ~20:30 | JTO成交量异动监控 | `Parameter bar error` | `getOKXKlines` 传 `'1h'`（小写），OKX 要求 `'1H'` |
| 3 | 05-08 ~23:00 | SPKTaker卖方主导预警 | API参数错误 | `period=4H` 不在 OKX rubik API 支持列表 `[5m, 1H, 1D]` |
| 4 | 05-08 ~23:18 | JTO多价位延迟确认监控 | `Parameter bar error` | `getOKXKlines` 传 `'1h'`（小写），OKX 要求 `'1H'` |

### 根因结论

**不是模板批量产出错误，是 API 封装设计缺陷 + 模板规范不够严格。**

1. **`getOKXKlines()` 不做参数映射**，直接透传给 OKX。而 `getKlines()`（CryptoCompare）内部有映射表 `1h→1H`。模型习惯性写小写 `'1h'`，对 CryptoCompare 安全但对 OKX 报错。
2. **模板中两种 API 混用**，未强制统一用哪个，模型自由选择时容易选错。
3. **OKX rubik API `period` 参数**只支持 `5m/1H/1D`，没有 `4H`，模板未列出白名单。
4. 三种不同错误模式（1h小写、4H不存在、SPOT/SWAP），不是同一个模板 bug 的批量复现。

### 建议修复方向

最有效方案：在 `getOKXKlines()` 内部加 interval 映射（和 `getKlines()` 一样），让小写自动转大写，从 API 层面消除问题。同时在模板中补充 OKX rubik API period 参数白名单。
